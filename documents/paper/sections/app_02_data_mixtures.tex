\section{Data Mixtures}
\label{app:data-mixtures}

Each data build fixes three things: the list of training languages, the English corpus and the sampling temperature across languages. This appendix describes how we choose the language lists, how we mix the languages, how large each build is, and the validation set that every model shares.

\textbf{Scheme A lists.} We derive the language lists from the FineWeb-2 per-language byte counts and from the benchmarks available in the evaluation harness. \emph{Scheme A} puts availability first. It ranks the FineWeb-2 subsets by the UTF-8 bytes of their training split, leaves out the subsets with no identified language, and takes the top $K-1$. The lists are nested. The $K=2$ list (Russian) is contained in the $K=8$ list (Russian, Chinese, German, Japanese, Spanish, French and Italian), which is contained in the $K=15$, $K=30$ and $K=50$ lists.

\textbf{Scheme B lists.} \emph{Scheme B} puts diversity first. It builds lists at $K \in \{8, 15, 30\}$ from the 49 largest subsets. It first takes the largest subset of each script not yet covered, then the largest subset of each language family not yet covered, and then the remaining subsets in order of size. At $K=8$, the scheme-B list spans seven scripts against four for scheme A. At $K=30$, it spans 14 scripts and 12 families against 10 and 10.

\textbf{Alternatives at $K \le 2$.} At $K=2$ there is no list to diversify, so the alternative builds change the second language. The scheme-B build \emph{ZH} replaces Russian with Chinese, and the scheme-C build \emph{ES} replaces it with Spanish. At $K=1$ there is no second language, so the alternative builds change the English corpus. Every other build uses DCLM-edu, the DCLM pipeline with an educational-quality filter. The scheme-B build \emph{DCLMP} uses the same pipeline without that filter. The scheme-C build \emph{FWEB} uses FineWeb restricted to the crawls up to 2022, which is DCLM's own Common Crawl window, so the two corpora do not differ in recency. All four alternative builds are trained on the deep ladder from 90M to 1.7B at seed 1904 (Table~\ref{tab:schemes}).

Table~\ref{tab:app-languages} lists the 99 FineWeb-2 languages of the sweep. For each language, it gives the smallest language setting whose scheme-A and scheme-B lists contain it, and the number of benchmark families that the harness offers for it.

\textbf{Mixture composition.} Every multilingual build blends English and FineWeb-2 50/50 at training time, through the blend weights of the Megatron data loader. The blend reads one English dataset and one FineWeb-2 dataset per build and language setting. Within the FineWeb-2 half, language $i$ receives a share $q_i \propto p_i^{1/T}$, where $p_i$ is its estimated token proportion in the corpus. At $T=1$ each language receives its share of the corpus, and $T=3$ flattens the distribution towards the smaller languages. The baseline build A uses $T=1$, and the temperature intervention AT3 uses $T=3$ on the same lists.

\textbf{No $K=100$ setting.} We also built a 100-language mixture with the scheme-A rule, from the 99 largest FineWeb-2 subsets, but did not train it, because the FineWeb-2 distribution is very skewed. At $T=1$, the largest language (Russian) would take 18.8\% of the multilingual half and the smallest 0.0038\%. At the 90M rung, 60 of the 99 languages would receive under 10M tokens. Flattening does not fix this, because the small languages run out of data. At $T=3$, the median language of the 92B build rises from 90M to 373M tokens, but the build then holds only 75.4B tokens, so the 1.7B rung, which draws 83.6B, would see its multilingual data 1.11 times. We therefore dropped the $K=100$ setting and train the temperature intervention on the scheme-A lists at $K=50$, with both the deep and the shallow ladder. We also train it at $K=30$ and $K=15$ with the deep ladder only. At these two settings, flattening leaves every language with enough data: under the 1.7B budget at $T=1$, the smallest language keeps 343M tokens at $K=30$ and 1.2B at $K=15$. A later version of the 100-language list replaces the eight subsets without a benchmark in the harness by the next subsets by size with at least two benchmark families. It was never built.

\textbf{Build sizing.} Each FineWeb-2 dataset is built to half of the largest token budget that trains on it, plus 10\% headroom. This gives 92B tokens for the 1.7B rung, and 165B for the 3B rung at the settings where it trains. The ZH build (52B) was sized when that build stopped at 1B, and its 1.7B run reads the same build. The English dataset is built once, to 184B tokens. The builder never repeats a document, so a language that runs out of data gives a smaller build. Smaller models draw a shuffled fraction of the same build, so within a setting all sizes see the same language proportions. Two kinds of build depart from a single pass over the data, and the analysis takes both into account.

\textbf{Repetition at $K=2$.} No single FineWeb-2 language can feed the 1.7B rung at $K=2$. A 1.7B model draws 83.6B tokens from the multilingual half, but the Russian build has 72.8B, so the 1.7B model at $K=2$ sees Russian about 1.15 times. The Chinese build (52.0B tokens) and the Spanish build (23.9B, all the Spanish that the source holds) are smaller still. At 1.7B, Chinese is seen 1.61 times and Spanish 3.51 times. At 1B, Russian, Chinese and Spanish are seen 0.65, 0.91 and 1.98 times. Repetition stays below 1.7 epochs across the Russian and Chinese ladders. For Spanish, it rises from 0.7 epochs at 350M to 3.5 at 1.7B, so every comparison of the $K=2$ builds reports these epoch counts.

\textbf{Extended builds.} The $K=15$ and $K=50$ builds of scheme A and the $K=15$ build of scheme B were first built to 52B. We extended them to 92B when we added the 1.7B rung at these settings. The extension continues the token stream of each language where the 52B build stopped, with later CommonCrawl dumps. The six deep and shallow 1.7B runs at these settings therefore read a superset of what their smaller proxies read. %\footnote{Verified byte for byte: every language section of each 52B build is a prefix of the corresponding 92B build.}

\textbf{Validation set.} Every model and every build share one fixed validation set. It covers English and the 99 FineWeb-2 languages of the built 100-language mixture, that is, the list before the eight benchmark swaps. For each language, it takes the first 5M tokens of the first parquet file of that language, but at most 30\% of the rows of the file, so that languages with a single file keep training data. The build records, for each language, the token count, the UTF-8 byte count and the number of leading rows assigned to validation. Every training build reads this record and skips exactly those rows, so training and validation data are disjoint by construction. Because one validation set serves the whole sweep, bits-per-byte is comparable across sizes, language settings and builds.
